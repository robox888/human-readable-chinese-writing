# 改写示例

[← 返回首页](../README.md)

每组示例都是作者构造的，用来演示规则。改写只调整表达，不新增原文没有的事实；原文缺的信息标成"待确认"。

### 规则 1：句子之间的关系要写出来

两句话挨着，第二句又不是第一句的直接延续，就要交代它们是转折、因果还是补充。读者不该自己猜。

| | 文本 |
|---|---|
| 改写前 | 新版本上线后转化率下降了 3%。客服工单量没变。我们决定先不回滚。 |
| 改写后 | 新版本上线后转化率下降了 3%，不过客服工单量没变，我们判断影响有限，所以先不回滚。 |

"我们判断影响有限"是补出来的理由。原作者的理由如果不是这个，就要先问清楚，不能替他编。

| | 文本 |
|---|---|
| 改写前 | 为什么 AI 文章越来越难读？后训练阶段的长度惩罚迫使模型压缩词数。 |
| 改写后 | 为什么 AI 文章越来越难读？一种解释要从训练目标说起。模型在后训练阶段会因为输出太长被扣分，于是倾向用更少的词塞进更多信息。 |

文章里自问自答时，问题后面加一句过渡。回答读者真正提出的问题时，直接给答案（见规则 7）。

### 规则 2：名词前的修饰语不超过两层

修饰语叠到三层以上，读者要在脑子里一层层拆。先把最里层的概念用一句话说清，再往外加。

| | 文本 |
|---|---|
| 改写前 | 请提交用户行为数据分析模型优化方案。 |
| 改写后 | 我们有一个分析用户行为数据的模型，请针对它提交一份优化方案。 |

| | 文本 |
|---|---|
| 改写前 | 基于多源异构数据融合的城市交通拥堵实时预测系统已上线。 |
| 改写后 | 城市交通拥堵实时预测系统已上线。它的数据来自多个来源、格式各不相同，系统会先把这些数据融合起来再做预测。 |

主语和动词之间也别塞太长的介词结构：

| | 文本 |
|---|---|
| 改写前 | 团队通过在资源有限的背景下对现有流程的系统性梳理发现了三个瓶颈。 |
| 改写后 | 资源有限，团队把现有流程系统地梳理了一遍，发现了三个瓶颈。 |

### 规则 3：少让抽象概念当主语"做动作"

"框架吞噬了时间""规则抓住了本质""机制驱动了增长"，这类句子偶尔一句没问题，一段里连着出现，读者就得不停把比喻翻译回实际意思。同一段最多两句，第三句起换成人或具体的事物做主语。

| | 文本 |
|---|---|
| 改写前 | 这个框架吞噬了团队大量时间。这条规则抓住了问题的本质。这套机制驱动了用户增长。 |
| 改写后 | 团队在这个框架上花了大量时间。按这条规则看，问题出在哪就很清楚了。用户增长主要靠这套机制。 |

| | 文本 |
|---|---|
| 改写前 | 数据揭示了用户的真实偏好，洞察推动了产品的迭代，反馈塑造了最终的设计。 |
| 改写后 | 从数据能看出用户真正的偏好。产品团队据此做了迭代，最终设计也参考了用户反馈。 |

### 规则 4：搭配要日常，注意分词边界

把每个"动词 + 宾语""形容词 + 名词"念出来，问自己：平时说话会这么说吗？

| 改写前 | 改写后 |
|---|---|
| 对齐一下颗粒度 | 把细节核对一遍 |
| 赋能业务闭环 | 帮业务把流程跑通 |
| 将其日历化 | 排进日程 |
| 沉淀方法论 | 把做法整理成文档 |
| 拉通上下游 | 跟上下游一起商量 |
| 打出组合拳 | 几项措施一起上 |

中文没有空格，有些字连在一起会让眼睛先切错词：

| 改写前 | 问题 | 改写后（按实际意思选） |
|---|---|---|
| 这些人才刚到 | "人才"还是"人 / 才刚"？ | 刚到公司的这批人才 / 这些人刚刚到 |
| 乒乓球拍卖完了 | "球拍 / 卖完"还是"球 / 拍卖完"？ | 乒乓球拍已经卖光了 / 乒乓球的拍卖结束了 |

### 规则 5：用常见短词，同一个概念别换着说

AI 改写倾向用更长、更少见的词，还会把同一个意思轮流换成不同说法。对模型来说这是"词汇丰富"，读者却得反复确认"方法""范式""路径"是不是同一个东西。

| | 文本 |
|---|---|
| 改写前 | 本方法可显著提升效率。该范式的核心在于自动化。这一路径的优势是成本低。借助此抓手，团队可快速落地。 |
| 改写后 | 这个方法能明显提高效率。它的核心是自动化，好处是成本低。用这个方法，团队很快就能用起来。 |

| 改写前 | 改写后 |
|---|---|
| 此举将对用户留存产生显著裨益 | 这样做能明显提高用户留存 |
| 擢升运营效能 | 提高运营效率 |
| 仰赖于第三方服务 | 依赖第三方服务 |
| 予以充分考量 | 认真考虑 |

### 规则 6：局部过渡要平滑，整体节奏有长有短

相邻句子之间别突然堆进一串新概念。整篇也别每句都一样长、一样的"主谓宾，从而主谓宾"结构。长分析句后面跟一句短句或一个具体例子，读者更容易跟上。

| | 文本 |
|---|---|
| 改写前 | 系统在高峰期出现了响应延迟，从而影响了用户的下单体验。团队对数据库连接池进行了扩容，从而缓解了部分压力。团队随后对慢查询进行了优化，从而将平均响应时间降低到了两百毫秒。 |
| 改写后 | 高峰期系统响应变慢，用户下单受到影响。团队先给数据库连接池扩了容，压力小了一些。接着优化慢查询。平均响应时间降到了两百毫秒。 |

### 规则 7：砍掉套话和过度作答

不用"值得注意的是""综上所述""不可否认的是""在当今……的背景下"。"不是……而是……"只用来纠正读者真实存在的误解或做数据对比，不当修辞。回答问题时先给结论，不复述问题，不列一堆意思重叠的选项，不在结尾把正文再说一遍。

**问题**：周报里要不要写没完成的事？

| | 文本 |
|---|---|
| 过度作答 | 这是一个非常好的问题。在当今快节奏的工作环境下，周报的作用不可忽视。值得注意的是，是否写未完成事项取决于多种因素：一方面，它能体现透明度；另一方面，也可能引起误解；此外，还要考虑团队文化。综上所述，建议根据实际情况灵活处理。 |
| 直接回答 | 要写。写清楚卡在哪、需要谁帮忙，看周报的人才能及时介入。 |

## 完整场景示例

### 场景 A：故障说明

**改写前**：

> 为什么线上服务昨晚出现了超时？基线系统状态转换延迟验证方案缺失。值得注意的是，团队需要尽快提交一份系统稳定性保障能力提升方案，并借力跨部门协同抓手对其颗粒度进行对齐。

**改写后**：

> 线上服务昨晚出现了超时。目前看，问题和系统状态转换有关：我们之前没有验证过基线系统在状态转换时的延迟。[待确认：这是否就是超时的直接原因]
>
> 接下来团队要尽快提交一份方案，说明怎么提高系统稳定性。方案的细节需要和相关部门一起核对。

要点：原文只说"验证方案缺失"，没说它就是超时原因。改写时不能写成"所以高并发一来就卡住了"，这句原文没有，只能标成待确认。

### 场景 B：产品介绍

**改写前**：

> 本产品深度融合 AI 能力，全面赋能用户内容创作全链路，通过智能化、场景化、个性化的解决方案矩阵，助力创作者实现效率与质量的双重跃升。

**改写后**：

> 这个产品用 AI 帮你写内容，从构思到成稿的各个环节都能用。它会根据你的写作场景给出不同建议，让你写得更快，也写得更好。

要点："全链路"换成"从构思到成稿的各个环节"，能列出产品真实支持的环节更好，但不能凭空编；"智能化、场景化、个性化"三连只保留有实际内容的部分；"双重跃升"换成"更快、更好"。

### 场景 C：技术说明

**改写前**：

> 该模块通过引入基于事件驱动的异步消息队列解耦机制，有效规避了上下游服务间强依赖导致的级联故障风险，从而显著提升了系统整体可用性。

**改写后**：

> 以前上游服务直接调用下游，下游一挂，上游跟着挂。现在中间加了一个消息队列：上游把消息放进队列就返回，下游自己去取。这样一个服务出问题，不会连带把其他服务拖垮。

要点：先说原来的问题，再说改法和效果；"解耦机制""级联故障"用一句具体描述代替；去掉没有数据的"显著"。
