# 让 AI 说人话：中文可读性写作 Skill

> **English**: A Chinese-writing skill for AI agents (Claude Code and other tools that read `SKILL.md`). It turns 2026 arXiv research on why AI-generated text is hard to read into seven checkable rules: explicit sentence relations, short modifier chains, concrete subjects, everyday collocations, consistent common words, varied rhythm, and no padding. Each rule comes with before/after Chinese examples below. MIT licensed.

AI 写的中文，每个字都认识，读起来却费劲。这个 Skill 把这种"费劲"拆成 7 个能逐条检查的问题，每条配改写前后的例子。它可以装进 AI 工具自动生效，也可以把规则复制进 `AGENTS.md` / `CLAUDE.md`。

## 一眼看懂：改写前后

**改写前**（典型 AI 味）：

> 值得注意的是，本次迭代通过对用户行为数据分析模型的优化，显著赋能了业务闭环。该方案吞噬了团队大量精力，这一路径的核心抓手在于对齐颗粒度。综上所述，团队需进一步将其日历化。

**改写后**：

> 这次迭代优化了分析用户行为数据的模型，业务流程因此跑通了。团队为这个方案花了大量精力，关键是先把细节核对清楚。接下来要把这件事排进日程。

改了什么：删掉"值得注意的是""综上所述"；拆开四层名词"用户行为数据分析模型"；"方案吞噬精力"改成"团队花了精力"；"方案 / 路径 / 抓手"统一说法；"赋能闭环""对齐颗粒度""日历化"换成日常说法。原文的"显著"没有数据支撑，改写时去掉了，没有替原文补数字。

## 7 条规则与例子

### 规则 1：句子之间的关系要写出来

两句话挨着，第二句又不是第一句的直接延续，就要交代它们是转折、因果还是补充。读者不该自己猜。

| | 文本 |
|---|---|
| 改写前 | 新版本上线后转化率下降了 3%。客服工单量没变。我们决定先不回滚。 |
| 改写后 | 新版本上线后转化率下降了 3%，不过客服工单量没变，我们判断影响有限，所以先不回滚。 |

"我们判断影响有限"是补出来的理由。原作者的理由如果不是这个，就要先问清楚，不能替他编。

| | 文本 |
|---|---|
| 改写前 | 为什么 AI 文章越来越难读？后训练阶段的长度惩罚迫使模型压缩词数。 |
| 改写后 | 为什么 AI 文章越来越难读？一种解释要从训练目标说起。模型在后训练阶段会因为输出太长被扣分，于是倾向用更少的词塞进更多信息。 |

文章里自问自答时，问题后面加一句过渡。回答读者真正提出的问题时，直接给答案（见规则 7）。

### 规则 2：名词前的修饰语不超过两层

修饰语叠到三层以上，读者要在脑子里一层层拆。先把最里层的概念用一句话说清，再往外加。

| | 文本 |
|---|---|
| 改写前 | 请提交用户行为数据分析模型优化方案。 |
| 改写后 | 我们有一个分析用户行为数据的模型，请针对它提交一份优化方案。 |

| | 文本 |
|---|---|
| 改写前 | 基于多源异构数据融合的城市交通拥堵实时预测系统已上线。 |
| 改写后 | 城市交通拥堵实时预测系统已上线。它的数据来自多个来源、格式各不相同，系统会先把这些数据融合起来再做预测。 |

主语和动词之间也别塞太长的介词结构：

| | 文本 |
|---|---|
| 改写前 | 团队通过在资源有限的背景下对现有流程的系统性梳理发现了三个瓶颈。 |
| 改写后 | 资源有限，团队把现有流程系统地梳理了一遍，发现了三个瓶颈。 |

### 规则 3：少让抽象概念当主语"做动作"

"框架吞噬了时间""规则抓住了本质""机制驱动了增长"，这类句子偶尔一句没问题，一段里连着出现，读者就得不停把比喻翻译回实际意思。同一段最多两句，第三句起换成人或具体的事物做主语。

| | 文本 |
|---|---|
| 改写前 | 这个框架吞噬了团队大量时间。这条规则抓住了问题的本质。这套机制驱动了用户增长。 |
| 改写后 | 团队在这个框架上花了大量时间。按这条规则看，问题出在哪就很清楚了。用户增长主要靠这套机制。 |

| | 文本 |
|---|---|
| 改写前 | 数据揭示了用户的真实偏好，洞察推动了产品的迭代，反馈塑造了最终的设计。 |
| 改写后 | 从数据能看出用户真正的偏好。产品团队据此做了迭代，最终设计也参考了用户反馈。 |

### 规则 4：搭配要日常，注意分词边界

把每个"动词 + 宾语""形容词 + 名词"念出来，问自己：平时说话会这么说吗？

| 改写前 | 改写后 |
|---|---|
| 对齐一下颗粒度 | 把细节核对一遍 |
| 赋能业务闭环 | 帮业务把流程跑通 |
| 将其日历化 | 排进日程 |
| 沉淀方法论 | 把做法整理成文档 |
| 拉通上下游 | 跟上下游一起商量 |
| 打出组合拳 | 几项措施一起上 |

中文没有空格，有些字连在一起会让眼睛先切错词：

| 改写前 | 问题 | 改写后（按实际意思选） |
|---|---|---|
| 这些人才刚到 | "人才"还是"人 / 才刚"？ | 刚到公司的这批人才 / 这些人刚刚到 |
| 乒乓球拍卖完了 | "球拍 / 卖完"还是"球 / 拍卖完"？ | 乒乓球拍已经卖光了 / 乒乓球的拍卖结束了 |

### 规则 5：用常见短词，同一个概念别换着说

AI 改写倾向用更长、更少见的词，还会把同一个意思轮流换成不同说法。对模型来说这是"词汇丰富"，读者却得反复确认"方法""范式""路径"是不是同一个东西。

| | 文本 |
|---|---|
| 改写前 | 本方法可显著提升效率。该范式的核心在于自动化。这一路径的优势是成本低。借助此抓手，团队可快速落地。 |
| 改写后 | 这个方法能明显提高效率。它的核心是自动化，好处是成本低。用这个方法，团队很快就能用起来。 |

| 改写前 | 改写后 |
|---|---|
| 此举将对用户留存产生显著裨益 | 这样做能明显提高用户留存 |
| 擢升运营效能 | 提高运营效率 |
| 仰赖于第三方服务 | 依赖第三方服务 |
| 予以充分考量 | 认真考虑 |

### 规则 6：局部过渡要平滑，整体节奏有长有短

相邻句子之间别突然堆进一串新概念。整篇也别每句都一样长、一样的"主谓宾，从而主谓宾"结构。长分析句后面跟一句短句或一个具体例子，读者更容易跟上。

| | 文本 |
|---|---|
| 改写前 | 系统在高峰期出现了响应延迟，从而影响了用户的下单体验。团队对数据库连接池进行了扩容，从而缓解了部分压力。团队随后对慢查询进行了优化，从而将平均响应时间降低到了两百毫秒。 |
| 改写后 | 高峰期系统响应变慢，用户下单受到影响。团队先给数据库连接池扩了容，压力小了一些。接着优化慢查询。平均响应时间降到了两百毫秒。 |

### 规则 7：砍掉套话和过度作答

不用"值得注意的是""综上所述""不可否认的是""在当今……的背景下"。"不是……而是……"只用来纠正读者真实存在的误解或做数据对比，不当修辞。回答问题时先给结论，不复述问题，不列一堆意思重叠的选项，不在结尾把正文再说一遍。

**问题**：周报里要不要写没完成的事？

| | 文本 |
|---|---|
| 过度作答 | 这是一个非常好的问题。在当今快节奏的工作环境下，周报的作用不可忽视。值得注意的是，是否写未完成事项取决于多种因素：一方面，它能体现透明度；另一方面，也可能引起误解；此外，还要考虑团队文化。综上所述，建议根据实际情况灵活处理。 |
| 直接回答 | 要写。写清楚卡在哪、需要谁帮忙，看周报的人才能及时介入。 |

## 完整场景示例

### 场景 A：故障说明

**改写前**：

> 为什么线上服务昨晚出现了超时？基线系统状态转换延迟验证方案缺失。值得注意的是，团队需要尽快提交一份系统稳定性保障能力提升方案，并借力跨部门协同抓手对其颗粒度进行对齐。

**改写后**：

> 线上服务昨晚出现了超时。目前看，问题和系统状态转换有关：我们之前没有验证过基线系统在状态转换时的延迟。[待确认：这是否就是超时的直接原因]
>
> 接下来团队要尽快提交一份方案，说明怎么提高系统稳定性。方案的细节需要和相关部门一起核对。

要点：原文只说"验证方案缺失"，没说它就是超时原因。改写时不能写成"所以高并发一来就卡住了"，这句原文没有，只能标成待确认。

### 场景 B：产品介绍

**改写前**：

> 本产品深度融合 AI 能力，全面赋能用户内容创作全链路，通过智能化、场景化、个性化的解决方案矩阵，助力创作者实现效率与质量的双重跃升。

**改写后**：

> 这个产品用 AI 帮你写内容，从构思到成稿的各个环节都能用。它会根据你的写作场景给出不同建议，让你写得更快，也写得更好。

要点："全链路"换成"从构思到成稿的各个环节"，能列出产品真实支持的环节更好，但不能凭空编；"智能化、场景化、个性化"三连只保留有实际内容的部分；"双重跃升"换成"更快、更好"。

### 场景 C：技术说明

**改写前**：

> 该模块通过引入基于事件驱动的异步消息队列解耦机制，有效规避了上下游服务间强依赖导致的级联故障风险，从而显著提升了系统整体可用性。

**改写后**：

> 以前上游服务直接调用下游，下游一挂，上游跟着挂。现在中间加了一个消息队列：上游把消息放进队列就返回，下游自己去取。这样一个服务出问题，不会连带把其他服务拖垮。

要点：先说原来的问题，再说改法和效果；"解耦机制""级联故障"用一句具体描述代替；去掉没有数据的"显著"。

## 怎么用

### 方式一：作为 Skill 安装

把本仓库放进你的 AI 工具的 skills 目录。以 Claude Code 为例：

```bash
git clone https://github.com/robox888/human-readable-chinese-writing.git \
  ~/.claude/skills/human-readable-chinese-writing
```

之后让 AI 写中文、润色、"去 AI 味"时，它会按 `SKILL.md` 里的 7 步执行，并在交付前逐条自检。其他支持 `SKILL.md` 的工具，按各自的 skills 目录放置即可。

### 方式二：复制到 `AGENTS.md` / `CLAUDE.md`

把下面这段贴进项目根目录的 `AGENTS.md`、`CLAUDE.md` 或系统提示词：

```markdown
## 中文写作可读性要求

面向人类读者的中文输出，遵循以下要求：

0. **不改原意**：改写不新增事实、理由、数字，不加强原文的确定程度。缺的信息标成 [待确认]，不替作者补。
1. **句间关系要写出来**：相邻两句不是直接延续时，用一个分句交代转折、因果或补充关系。文章里自问自答可加一句过渡；回答读者的问题时直接给答案。
2. **修饰语不超过两层**：名词前的定语超过两层时，先用一句话说清最内层概念再往外加。不写"用户行为数据分析模型优化方案"这类名词堆叠。
3. **少让抽象概念当主语做动作**：同一段里"这个框架吞噬了……""这个机制驱动了……"这类句子最多两句，之后换成人或具体事物做主语。
4. **搭配要日常**：逐句检查动宾和修饰搭配，平时说话不会这么说的（"对齐颗粒度""赋能闭环""日历化"）换成日常说法；避开容易切错词的字序。
5. **用常见短词，术语一致**：同一概念在一段内只用一种说法，不轮换"方法 / 范式 / 路径 / 抓手"；能用常见词就不用生僻词。
6. **局部平滑，整体有长有短**：相邻句子衔接自然；句子长短交错，长分析句后可跟一句短句或具体例子。
7. **砍掉套话和过度作答**：不用"值得注意的是""综上所述""不可否认的是""在当今……背景下"；"不是……而是……"只用于纠正真实误解或数据对比。先给结论，不复述问题，不列重叠选项，不写重复总结。
```

## 研究依据与证据强度

规则参考了 2026 年 6 月至 10 月发表在 arXiv 上的 9 篇论文。下表列出每篇的核心结论，数字已对照论文全文核对。

| 论文 | 核心结论 | 支撑规则 |
|---|---|---|
| Clark, Martin & Mahowald, *Why is AI-generated language so hard to understand?* [arXiv:2610.29162](https://arxiv.org/abs/2610.29162) | 采集了 14 个模型的文本。和人类写作相比，9 个前沿模型都更多使用"无生命主语 + 有生命动词"和低频词组，多数还更常用长依存、名词堆叠和省略关系词的从句。作者提出的解释是：数学、代码、推理类后训练带来"信息密度压力"，并用长度惩罚微调实验做了概念验证。 | 1、2、3、4 |
| Cekini et al., *The Cognitive Cost of LLM Writing* [arXiv:2610.23715](https://arxiv.org/abs/2610.23715) | 496 组"人类原文 / AI 改写"对比，用英文眼动数据训练的模型预测阅读时间：AI 改写词数少 2.66%，但每词预测阅读时间多 1.57%；词更长（+6.06%）、更少见（词频 −7.61%）、词汇多样性更高（MTLD +31.83%）。 | 5 |
| Li & Xu, *UIDPO* [arXiv:2610.14578](https://arxiv.org/abs/2610.14578) | 基于"均匀信息密度"理论设计偏好优化：允许整体信息密度有较大起伏，但要求局部过渡均匀（"分段线性"）。在英文补语从句分析里，该方法正确保留必要连接词 *that* 的次数比基线多 36.57%。 | 1、6 |
| Zhu et al., *LM Surprisal in Reading Chinese* [arXiv:2610.04898](https://arxiv.org/abs/2610.04898) | 在三个中文眼动语料库上，语言模型的"意外度"能预测中文阅读时间，但模型越大是否越准因语料而异。在新闻语料 HKP 上，越接近局部二元 / 三元词组统计的模型，预测越准。 | 4 |
| Shan, Lee & Hao, *AI Writers Have a Consistent Stylometric Footprint* [arXiv:2608.27855](https://arxiv.org/abs/2608.27855) | 8 个模型、5 个领域：AI 生成文本的信息熵比人类高约 1 个标准差，词汇多样性高约 2 个标准差，这是最稳定的特征。 | 5 |
| El Attar et al., *Linguistic Features in AI-Generated Text Detection* [arXiv:2606.04177](https://arxiv.org/abs/2606.04177) | 27 个模型、10 个领域、284 个语言特征：词汇丰富度是跨模型、跨领域最稳定的 AI 文本信号。 | 5 |
| Massaro, *Literary Non-Style in LLM-Generated Text* [arXiv:2607.17228](https://arxiv.org/abs/2607.17228) | AI 文本在三元、四元词组层面反复使用固定套话，同样篇幅里承载的语义内容更少。 | 7 |
| Hu et al., *When LLMs Over-Answer* [arXiv:2607.17063](https://arxiv.org/abs/2607.17063) | 在硬件描述语言（芯片设计用的编程语言）问答中，工程师认为 65.7% 的 AI 回答堆了重复备选（人类采纳答案 4.4%），69.1% 有多余铺垫和总结（人类 5.8%）。不过 58.3% 的情况下，参与者觉得 AI 回答更好读。 | 7 |
| Zhu et al., *LLMs Do Not Always Need Readable Language* [arXiv:2606.19857](https://arxiv.org/abs/2606.19857) | 提示模型放弃"人类可读"约束后，模型会写出人看不懂的压缩文本：长度只剩原文 27.9%，模型仍能恢复 99.5% 的语义。说明"模型能读懂"和"人能读懂"可以部分分开。 | 背景 |

**证据强度说明**：

- **有直接研究支撑的**：AI 文本更多使用抽象主语、名词堆叠、低频搭配（规则 2、3、4）；用词更长更少见、词汇多样性虚高（规则 5）；套话和过度作答（规则 7）。
- **由研究推断的**：句间关系写清楚、局部平滑（规则 1、6），来自均匀信息密度理论和英文连接词分析。
- **经验做法**：所有数字阈值（两层、两句、6–12 字）和分词边界检查，都是写作经验，论文里没有这些数值。

## 局限

- 9 篇论文里只有 1 篇研究中文，其余都基于英文。把结论迁移到中文是推断，没有经过中文读者实验验证。
- 规则针对说明文、报告、文章和技术文档。诗歌、法律文本、需要固定术语的规范文件，可能要例外处理。
- 规则改善的是"好不好读"，内容本身对不对、全不全，需要另外检查。

欢迎在 Issue 里贴你的改写前后对比，或指出规则不适用的场景。
